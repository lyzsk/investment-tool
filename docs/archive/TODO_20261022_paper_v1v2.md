### 16:3x · 回你 16:25「claude -p 一直开着 vs 每次 --resume；Agent SDK 和它比好在哪」

**先说共同点（决定性的）**：这三种底下都是同一个 Claude Code 程序、走同一个中转和 key，对模型来说每一轮都是"把整段对话历史再发一遍"——质量一样，贵不贵都取决于缓存能不能命中。区别全在工程上：启动开销、崩了怎么办、我们怎么控制它

**A1 · claude -p 一直开着（流式输入模式，一个进程跑一整天）**
- 好处：没有每次启动的开销；可以在它想的过程中打断、插话；状态都在内存里
- 坏处：进程挂了 / key 轮换（每 4 小时自动换一次）/ 07:58 换会话，都要处理重连；我们要写一个"往它 stdin 里塞消息、从 stdout 读结果"的驱动；Windows 上长期跑的稳定性我没实测过

**A2 · 每次触发起一个新 claude -p，带 --resume 接着同一个会话**
- 好处：最稳——每次都是新进程，崩了下次照样接上；key 轮换后下一次自动用新 key；**现成的 `claude_call.py` 已经支持 --resume**（重试、额度窗口等待、花费记账都有），改动最小
- 坏处：每次多几秒启动 + 读会话记录（和动辄几分钟的思考比可以忽略）；不能中途打断，只能等这一轮答完
- **A1 vs A2：我选 A2**（置信 65%）——paper 要的是一整天不出事，几秒启动开销不值得换稳定性

**B · Claude Agent SDK**
- 本质：把 Claude Code 包成 Python 库，**底下照样启动 Claude Code**，所以质量、价钱、缓存表现和 A 一样
- 比 A 好的地方（都是工程层面）：①会话是代码里的一个对象，"发消息 / 拿回复"是函数调用，不用拼命令行、解析输出 ②回复是结构化的（文字、工具调用、花费、用量分开），不用正则抠 ③有钩子：可以在它每次要读文件 / 调工具前拦一下（比如禁止它写账本、记日志）④权限、可用工具在代码里配
- 坏处：要新装一个库（本机还没装）、我们现有的那套 claude_call.py（key 轮换、额度窗口、记账）要重新接一遍；它对 gravitex 中转的兼容性没实测（理论上一样，因为底下就是 Claude Code）

**建议（置信 60%）**：先用 A2（改动最小，明后天就能跑起来），v3 稳定后再评估迁到 B；今晚的 $1 实验加一项：同一份材料用 A2 连续 --resume 3 次，量启动开销和缓存命中——命中率上不去的话，三种方式都白搭，那就得先解决中转的问题

### 16:2x · 回你 16:19「塞不下 + 盘中读又太慢，是不是无解 / 一线一个 claude -p 对不对 / 能不能共用 / 进程调 API 已证伪还有别的方式吗」

**① 不是无解 —— "塞不下"是我们自己设的上限，不是模型的限制（置信 85%）**
- 事实：芷影 skill 全部文本（画像 + 规则 + 案例 + 指纹）约 20 万字节、刘忆青 19 万、土豆 11 万，折合约 7~10 万 token；Opus 5.5 的上下文是 100 万 token，**整份灌进去绰绰有余**
- 那为什么设 64KB 上限？因为现在的架构是"每次触发 6 次请求、每次都把材料从头再发一遍"——材料越大，每次越贵越慢。而今天的数据把问题坐实了：**全天 492 次成功调用，缓存命中率只有 3.6%**（写缓存 4292 万 token、读缓存只有 169 万），等于每次都按全价重读、重新付"写缓存"的钱
- 所以真正的解法不是"挑着给"，是**"灌一次、反复用"**：同一个会话早上灌全量，之后盘中每次只追加"变了什么"，前面的材料走缓存（缓存读价只有全价的 1/20，Opus 5.5 输入 $4 / 百万、缓存读 $0.20 / 百万；缓存 TTL 有 5 分钟和 1 小时两档）→ 材料全给、每次又快又便宜。这也正是 AI 的优势能用上的方式：最宝贵的沉淀不再被截断
- 再加一层：每晚用一次长时间的离线研究（不赶时间）把全量材料压成"作战手册"（情境 → 动作的对照表 + 引用原文位置），早上手册 + 全量原文一起灌；手册让模型盘中秒定位，原文保证不丢细节

**② 一条线一个 claude -p 对不对 / 能不能共用（置信 70%）**
- 拟人线（土豆 / 刘忆青 / 芷影）**必须各自一个会话**：三个导师的人设、规则互相冲突，放一个会话里会串味，拟人度更上不去；而且一个会话同一时刻只能处理一件事，三条线共用就得排队，竞价窗口会被挤掉
- 决策T 线（纳指 / 中行）**可以共用一个会话**：任务同类（单品种做 T）、材料小（各 1~2 万字节）、触发不频繁，共用省一份上下文；坏处是两边同时触发要排队（纳指和中行的波动时段错开，影响小）
- 所以建议 4 个会话：土豆 / 刘忆青 / 芷影 各一个 + 决策T 共用一个

**③ "进程调 API"不算证伪，证伪的是"每次重建上下文"这种用法；可选的承载方式有三种**
- A. **claude -p 常驻会话**：用流式输入模式让一个 claude -p 进程一直开着、按回合接收新消息（或者每次触发用 --resume 接着同一个会话）；自带重试、能自己读文件；缺点是我们现在只能"往窗口里打字"来注入，比较土
- B. **Claude Agent SDK**（把 Claude Code 当 Python 库用）：一条线一个长期会话对象，代码里直接"发消息 / 收回复"，自带读文件工具、重试、上下文管理，不用往窗口打字——**这是 A 的正规做法，我推荐这个**（文档 code.claude.com/docs/en/agent-sdk）
- C. **Messages API 多轮对话**（就是现在的直连 API，但改用法）：每条线维护一份对话记录，材料放 system 并打 1 小时缓存，每次触发只追加一条 user 消息；长了用服务端压缩。最可控、最省，但读文件之类的工具要自己写
- 这三种都依赖同一个前提：**缓存要真的命中**。今天 3.6% 的命中率很可能是中转（gravitex）的问题——不同请求被分到了不同上游。这一条不解决，A / B / C 都会贵
