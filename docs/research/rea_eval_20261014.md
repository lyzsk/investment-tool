# REA 逆向工具评估 + 数据采集机械化（2026-10-14 凌晨）

> 范围：用 REA（rea-agents@6.4.0，MIT）调研 7 个方向，给出结论：已上线 / 需用户定 / 不建议。冒烟时间 01:20~02:05，非盘中，没碰东财 0915 时段。
> 证据：抓包证据与探针脚本在 `scripts/temp/rea_1014/`（REA 抓的 `*.json` 跑完已删，只留探针脚本和回滚备份 `*.bak_1014`）。

## 0. REA 在本机能干什么

`npx -y rea-agents@6.4.0 capabilities` 实测结果（未装 MCP，未改 ~/.claude，只走 npx CLI）：

| 能力 | 本机 | 对我们有用吗 |
|---|---|---|
| **capture-browser-scenario**（Playwright 无头 + 本机 Chrome，抓网络请求/响应体） | ✅ 可用（headless 默认，临时 profile 用完即删，零弹窗） | **最有用**：一次 10~40s，拿到页面真实调用的接口、参数和响应体。本次财联社和同花顺的接口全是用它找到的 |
| inspect-web-page / list-browser-targets（CDP 被动观察） | ✅（要先开一个带调试端口的浏览器） | 一般，scenario 已经够用 |
| inspect-web-network-capture（HAR 回放分析） | ✅ | 备用：用户手机抓的 HAR 可以拿来分析 |
| analyze-javascript-application（静态解析 JS/Electron 包） | ✅ | 中：能拆 Electron 客户端；网页 bundle 用 grep 更快 |
| inspect-android-package（APK 反编译） | ❌ 需要 JADX + JDK（JDK17 有，JADX 没装） | 低：H5/网页已经覆盖需求，没必要 |
| Ghidra / IDA / Hopper（原生二进制） | ❌ 没配 provider；Hopper 不支持 Windows | 不需要 |
| macOS 系列、adb | ❌ / 需要设备 | 不需要 |

**一句话**：REA 对我们的价值 =「无头浏览器抓包 → 找到接口」这一步，省掉人工开 F12 的环节。找到接口以后，生产脚本直接用 `fetch` 请求，**不依赖 REA**，因为一次 REA 运行要 10~40s，还会起一个 Chrome，不适合放进 cron。用法封装在 `scripts/temp/rea_1014/scen.mjs`（URL 进，抓包证据 JSON 出）+ `urls.mjs`（列出请求）+ `bodies.mjs`（在响应体/JS 里按正则搜接口路径）。

## 1. 各方向结论

### ① B站发现 —— **已上线**（双源 + 熔断）
- **调研**：REA 帮不上，B站要的是 WBI 签名和风控知识，不需要抓包。用纯脚本探针实测了 4 个列表接口：
  - `x/space/wbi/arc/search`：现主路，要 WBI 签名，带 `mid/is_union_video/is_charging_arc` 字段。
  - `x/series/recArchivesByKeywords?mid=&keywords=&orderby=pubdate`：**不用签名**，只要 buvid cookie 和 space Referer，返回 `bvid/pubdate/duration/state/upMid`。10/14 实测桃哥前 10 条和主路逐条一致。
  - `x/polymer/web-dynamic/v1/feed/space`（动态流）：签名后仍然返回 -352 或空，**不可用**。
  - `seasons_series_list`（合集列表）：免签名可用，但只有合集元数据。
- **风控实测**：几分钟内连发约 25 次 B站接口后，整个 IP 返回 412 HTML，十来分钟后自愈；之后单轮 4 个请求偶尔也会撞上一次 412。
- **上线内容**（`scripts/bilibili/fetch_bilibili.mjs`）：
  1. 发现改为 ①WBI 投稿列表 ∪ ②recArchives 两源取并集，各自失败互不影响。①失败先自重试一次。两源都失败才降级到旧的搜索 + BFS 路。
  2. **每轮请求数从 13 次降到 4 次**：--list 不再逐条调 view，因为 Java 只消费 bvid/title/pubdate/mid/duration，这些两源列表都自带；下载模式按 bvid 现取 view，归属闸不变。
  3. 对账日志：在两源共同覆盖的时间窗里，一源有、另一源没有的 bvid 打到 stderr（进 sys_job_log）。
  4. 搜索兜底路加熔断：连续 3 次风控 HTML 就停，避免再打 80 次 view 把封禁拖长。
- **冒烟**：三 UP × 2 轮共 6 次 exit=0，每次 2~5s（旧版 8s，搜索路要 60s+）。其中 4 次是源②被 412、源①独自撑住，1 次是两源同时 412、降级后重试成功。下载模式 `--bvid … --audio-only` 回归通过。
- **回滚**：`cp scripts/temp/rea_1014/fetch_bilibili.mjs.bak_1014 scripts/bilibili/fetch_bilibili.mjs`。
- **"找准"的剩余缺口（未做，进 TODO）**：
  - 多 P：downloadProducts 只取 view 的首个 cid，多 P 稿后面几 P 会丢；应遍历 `pages[]`。
  - 充电专属：`is_charging_arc=true` 的稿，playurl 只给试看片段；应在发现段标记并跳过或告警。
  - 删改重发：新 bvid 会被当作新稿；可按「标题相似 + 时长差 <10%」在 48h 内去重告警。
  - 联合投稿：mid 过滤会剔除「本人只是 staff」的稿，口径和旧 view 归属闸一致；要不要收由用户定。
  - 动态里发的视频：动态 feed 不可用；目前投稿列表已经包含动态发的稿，暂无证据表明会漏。
  - **对账方法**：每轮 ①∩② 共同时间窗内的差异看日志；每周跑一次「搜索路」做第三源全量对比（手动 `--list` 时临时禁用双源即可）。

## 3. 不自信点
1. B站 412 是这次探针连发引起的，还是本 IP 已被标记？平时 cron 每小时 1 轮 × 4 次请求，应该远低于阈值，但未经长期验证。
2. recArchives 是「合集/系列」相关接口，B站以后可能收紧；它只作第二源，挂了不影响主路。
3. 财联社 x-quote 免签名，可能是对方的疏忽，随时可能补上签名。所以只作备源，不作唯一源。
4. 财联社 `limit_up_days` 和东财 `zttj.ct` 口径不同：澳弘电子东财记 10（17天10板），财联社记 1，因为当天断板后又首板。梯队用哪个口径要你定。
5. 早报 --discover 依赖专题页 HTML 结构（正则），改版时出口 6，会提示人工贴链接，不会写错数据。
