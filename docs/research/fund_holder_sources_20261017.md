# A5 公募基金持仓 + 十大流通股东里的"牛散"：获取方案（2026-10-17）

> 回答你的问题："准备怎么获取公募基金持仓 + 十大流通股东里的牛散，别忘了爬虫的健壮性，以及我们目录结构的特点"。
> **证据来源**：10/17 中午每个源 1~5 次小样本实测，原料在 `downloads/holders/_probe/`。上午误开的 agent 只打了探测请求就被我停了，没写正式代码；本文是我在主会话里根据这些样本写的。
> 标注：【实测】= 样本里亲眼看到；【推测】= 文档 / 经验，没验证。

## 一、结论先行

- **数据源**：主源全部用**东财 datacenter**（一个域名、JSON、可按报告期 / 股东类型 / 股东名过滤），备源用**新浪 F10 页面 + 天天基金 F10 + 蛋卷基金 API**（不同站点，不会和主源一起挂）。
- **"牛散"不用自己从零识别**：东财有现成的"个人股东协同分析"报表 `RPT_COOPFREEHOLDERS_ANALYSIS`。2026-06-30 这一期个人股东 19533 行，带出现次数和上榜后 10/30/60 日涨跌【实测】，直接可以拿来按"多期出现 + 上榜后表现"筛人。
- **请求量不大**：
  - 全市场十大流通股东一期约 5.6 万行，按 500 行一页约 113 次请求；
  - 按现有东财 datacenter 的节奏（2.5 秒一次 + 抖动）约 5 分钟一期，回溯 8 期约 40 分钟；
  - 现有日预算 3000 次够用。
- **能学到什么**：选股和配置（他们季度末拿着什么、新进了什么、加减了什么）；**学不到择时**（季度粒度，而且披露滞后 0.5~4 个月）。适合当"中长线导师"或给现有导师当候选池的先验，不能替代短线导师。
- **建议分三期**：①只落数据（零 token，约 1 天工作量）→ ②研究哪些牛散 / 基金经理"上榜后持续跑赢"（零 token）→ ③再决定要不要建 1~2 个季度级的牛散 / 基金经理 skill（那时才花 token）。

**披露节奏**【推测，按法规】：
- 季报：前十大，季度结束后 15 个工作日内；
- 中报：全部持仓，8 月底前；
- 年报：全部持仓，次年 3 月底前；
- 上市公司的十大流通股东随一季报（4 月底）、中报（8 月底）、三季报（10 月底）、年报（4 月底）陆续出，所以每年 4、8、10 月是集中更新期。

## 三、健壮性方案（按我们现有的请求层和"失败在脚本内闭环"的规矩）

1. **全部请求走 `scripts/lib/req_guard.py`**：
   - 东财 datacenter 已有配置 `em_datacenter`：2.5 秒间隔 ± 抖动、连败 4 次熔断 30 分钟、403/429 当封禁冷却 120 分钟、日预算 3000，直接复用；
   - 新浪已有 `sina` 源；
   - 只需新增 2 个独立熔断的源：`em_fundf10`（天天基金 F10 / pingzhongdata）、`danjuan`（蛋卷），建议间隔 1.5 秒、日预算 1000。
2. **主备自动切换**（switch-case 转移）：
   - 主源失败按类型处理：BLOCKED / RATE_LIMIT 熔断后切备源；PARSE 记下样本、切备源；NO_DATA 记"本期未披露"，不算失败。
   - 备源也失败就跳过这只或这一页，记进 manifest 的 missing，**不拖垮整批**。
3. **逐请求落盘缓存 + 断点续抓**：
   - 每页原始响应存 `downloads/holders/<源>/<报告期>/p<页号>.json`，已存在就不再请求；
   - 断了重跑即续，同 `index_constituents.py` 的做法。
4. **完成判定**：
   - 一期抓完写 `DONE` + `manifest.json`，内容包括应有页数（接口返回的 pages）、实到页数、行数、缺失列表、用的源；
   - 行数和接口 count 对不上就不写 DONE。
5. **增量判断"新一期出没出"**：
   - 按公告日（NOTICE_DATE / UPDATE_DATE）倒序拉第 1 页，看有没有比本地新的；
   - 有才拉这一期新增的部分；披露季（4、8、10 月）每周拉一次，其余月份每月一次。
6. **健康检查**：
   - daily_health 加一项"最新报告期完整度"：已披露公司数和上期比、缺失页数、最后成功时间；
   - 有红就主动报，同 10/14 的爬虫规矩。
7. **节奏**：
   - 只碰 datacenter / F10 / 新浪 / 蛋卷，**不碰东财 push2**（25 次 / 5 分钟会封）；
   - 首次回溯分 2~3 个晚上跑完，每晚不超过日预算的一半。

## 四、目录结构（按"域"组织，和现有 market / tzzb / lhb 一致）

```
scripts/holders/                      ← 新域
  fetch_holders.py   fetch  原料抓取(按报告期/股东/基金, 主备切换, 落盘缓存, DONE+manifest)
                     build  零请求: 原料 → 规范化 jsonl(股东持仓 / 牛散统计 / 基金持仓), 统一代码口径(a_rules 识别品种)
                     import [--commit] 默认 dry-run; 要入库时整期在一个事务里写(建表 SQL 先放 sql/todo/ 给你审)
  niusan_screen.py   零 token: 按"多期出现 + 上榜后 30/60 日超额 + 持仓市值门槛"筛牛散候选, 出报告
downloads/holders/
  em_freeholders/<报告期>/p001.json …  DONE  manifest.json
  em_coop/<报告期>/…
  em_fundpos/<基金代码>/<报告期>.json
  fund_meta/fundcode_search.js  nav/<基金代码>.js  manager/<基金代码>.html
  _probe/                              ← 今天的小样本(可删)
```

- 挂进 check md：`--only holders`，周六跑（披露季每周、其他月份每月第一个周六），失败退出码进定时任务提醒。
- 是否建表：一期先**只落文件**，等真有 SQL 查询或前端需求再建（同开盘 15 分钟数据的处理）；表结构草案先写进 `sql/todo/`，不执行。

## 五、能学到什么、学不到什么

- **能学**：
  - 选股偏好：行业、市值、估值区间、新进还是加仓；
  - 持有期：同一只票跨几期；
  - 配置集中度；
  - 牛散"上榜后表现"本身就是一个现成的业绩标签。
- **学不到**：
  - 买卖点和择时：季度末快照，中间做了什么看不到；
  - 仓位变化的时间点；
  - 滞后最长近 4 个月（年报）。
- **偏差**：
  - 十大流通股东只看到"刚好进了前十"的持仓，小仓位看不到；
  - 牛散协同表是东财的口径，"出现次数"和名字归一（同名不同人）要我们自己再核；
  - 基金季报只有前十大。
- **和现有导师的关系**：现有 17 位基本都是短线，这条线补的是"中长线 + 机构 / 大户的选股"，属于分散来源。最可能的落地方式是两种：
  - 给现有链的候选池加一个"近期有牛散 / 绩优基金新进"的标记（零 token）；
  - 单独 1~2 个季度级 skill，用月度调仓的 paper 账本，不跑盘中链。

## 六、工作量与需要你拍板的点

- **工作量**：一期（抓取 + 规范化 + 健康检查 + check md 挂钩）约 4~6 小时；首次回溯 8 期约 1~2 个晚上（自动）。二期筛选报告约 2 小时。全部零 token。
- **要你拍板**：
  1. 做不做一期（只落数据）；
  2. 回溯几期（建议 8 期 = 2 年）；
  3. 基金范围：全部主动权益约几千只每期就要几千次请求，建议只跟"任职 ≥5 年、业绩靠前"的 50~100 位经理，名单二期再定。

## 七、我不确定的

- 季报是不是只给前十大、中报 / 年报是不是全部持仓，只看了一只基金的年报样本（275 行），季报没测。
- 东财 datacenter 的真实封禁阈值没摸到（10/14 回填龙虎榜时 0.2 次 / 秒连跑 2 小时零限流），首次回溯前先小批量试。
- 牛散协同表的"上榜后 10/30/60 日涨跌"是从哪天起算（截止日还是公告日）没核实。公告日之前的涨跌我们拿不到也用不上，这个必须核清楚再用。
