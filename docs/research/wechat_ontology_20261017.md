## 一、两篇在说什么（各 3 句）

**第 1 篇**：
- 企业已经有了数仓、指标平台、知识图谱、AI 上下文层，却仍然每做一个新应用就重新梳理一次业务、重写一次口径。
- 作者把现有路线分成五类：数仓语义、指标本体、W3C 正式本体（RDF/OWL）、AI 上下文本体（如 Databricks Genie Ontology）、操作型本体（Palantir 式，对象 + 行动 + 权限）。
- 真正贵的是"同一个业务概念在每个系统、每段提示词、每份代码里各定义一遍"，以及由此带来的反复集成。主张是对象、关系、指标、行动、智能体围绕**同一份业务模型**协同，一处定义、到处复用。

**第 2 篇（30 道题里对我们有用的部分）**：
- 本体、语义模型、知识图谱、图数据库是不同层：本体回答"是什么意思"，图数据库回答"怎么存"。
- 好本体的评判维度：业务覆盖、语义一致、数据可映射、可计算、可查询、可执行、可维护（第 12 题）。
- 第 15 题：结构合法 ≠ 事实真实，事实真实 ≠ 现在仍然有效。
- 第 14 题：实体解析，即跨系统同一个东西被识别成多个。
- 第 16 题：版本管理。
- 第 21 题：本体减少幻觉，靠的是"语义约束 + 权威数据 + 执行验证"三者一起。
- 第 25 题：可靠的 Agent 要有工具契约、执行控制、结果验证和可观测性。

## 三、建议（按性价比排；都是零 token 的工程活，要不要做由你定）

1. **建一个"导师登记表"当唯一真源**（性价比最高）。
   - **做法**：把 `scripts/tzzb/tzzb_ledgers.json` 扩成全体链的登记表（或者另建 `scripts/lib/mentors.json`）。
   - **字段**：id、显示名、类型（UP / tzzb / 对照）、账本名、短描述、风格簇、能力圈一句话、上线日。
   - 上面约 18 处写死的名单全部改成读它（py / mjs 各写一个 5 行的读取函数）。
   - **效果**：以后加导师 = 登记表加一行 + 建 skill 目录。今天这种"改 18 个文件"的入库，以后改 1 个。
   - **风险**：一次要改很多文件，必须逐个 selftest；周末、链不跑的时候做最安全。
2. **品种识别只留一份**：代码 → 市场 / 板块 / 品种（股票、转债、ETF、指数、港股）的判断全部走 a_rules，各脚本删掉自己那套正则。
3. **产物"形状"校验集中化**：md 小节、各链 contract、downloads 的 DONE/manifest，统一成一个 schema 目录 + 一个校验器，daily_health 统一报。以后新增一种产物只加一个 schema。
4. **不建议做的**：引入图数据库或本体平台、把数据改成 RDF。我们的实体只有几千只股票 + 十几位导师 + 几十个板块，关系查询 MySQL 足够；复杂度会远超收益（奥卡姆剃刀）。

## 第 3 篇：《本体智能 | 一文读懂企业级本体模型》（10/17 下午 agent 补）

> 出处：公众号「华力江海」，发布于 2026-05-30，https://mp.weixin.qq.com/s/UJKyUQ9rpeMJ31bSLlz32w 。原文存 `downloads/wechat/_research/UJKyUQ9rpeMJ31bSLlz32w.html/.txt`（正文约 8900 字）。
> **性质**：方法论科普 / 架构框架文。正文没有推销产品，但也**没有案例、没有数据、没有效果评估**，大量是"统一、规范、闭环、无遗漏"一类的套话。只能当一份"检查清单"用，不能当证据。

### 一、文章要点

1. **四要素建模**：每一层本体都用同一套写法——实体类型、实体属性、语义关系、领域公理（"公理"=不随场景变的硬约束，要能机器校验）。
2. **五层架构**（从企业 4A 架构 业务/数据/应用/技术 归纳出来）：M1 实体（静态数据底座）→ M2 行为（流程、环节、原子操作、MCP 服务、原子 Agent）→ M3 规则（通用公理、阈值规则、合规校验、风险预警）→ M4 场景（复用 M1~M3 做编排）→ M5 角色（岗位、账号、权限）。
3. **M3 规则要结构化**：阈值规则的字段是"管控指标、临界数值、触发条件、处置动作"；公理包括"制度溯源"（每条规则必须能指到出处）、"阈值唯一"（同一指标全局只有一个阈值）、"违规必处置"。
4. **M4 资源复用公理**：底层资产多场景复用，"杜绝同质化重复建设"。
5. **M2 流程时序公理**：环节严格按前置依赖执行；Agent 只能在绑定的场景里触发。
6. **M5 最小权限公理**：每个角色只给完成任务所需的最小权限。

### 三、建议（按性价比排）

1. **修 4 份 chain.md 拟人审里的错名**（零 token，几分钟）。zhiyingjuexin 改成"芷影攫心"，三位新导师改成各自的显示名。属于 bug 修复，不算新决策，**建议主会话在 10/19 周一 08:05 前顺手修掉**（chain.md 属于 skill 文件，按规矩由主会话改）。
2. **加一个零 token 的"盖章漂移检查"**，挂进 `scripts/health/daily_health.py`（零 token，小活，不需要拍板）。做法：每份 chain.md 把导师 id 和显示名替换成占位符、剔除能力圈 / 推导链 / 取数这几段，再和 taoge 模板比对；出现非预期差异，或文中出现别的导师的名字，就报红。这样不用动架构，就能先把第 1 条这类问题拦住。
3. **chain.md 改成"1 份模板 + 每位导师一组变量"**（零 token，但要改驱动器，**需要用户拍板**，建议和二B-4 导师登记表一起在周末做）。变量包括显示名、id、能力圈、推导链、取数、时段，可以直接放进二B-4 的登记表。taoge、buchitudou0（转债，13KB）、control（对照组）结构本来就不同，保留成"模板 + 覆盖段"。做完以后，像方案 A 这种全局改动只改 1 处，不用再写 apply_plan_a 这种批量补丁。代价：`chain_md_sha12` 指纹口径要改成"模板 hash + 变量 hash"。
4. **规则字段补"出处"和"阈值"**（token 增量几乎为零，可以顺着 TODO 三-2 默认做）。蒸馏提示词要求新规则固定输出：方向 / 触发条件 / 临界数值 / 处置动作 / 出处（md 日期或账本腿）/ 验证状态，rule_tags 一并抽取。目的是把"话术级 107 条"里能写成数字的逐步转成可校验的；不要求旧规则一次性改完。
5. **不建议做的**：照搬 M1~M5 五层或 4A 映射。我们没有组织、岗位、审批流，M5 在我们这里就是"每一步能看到什么"，已经做了；再套一层框架只会多出文档，不会多出能力（奥卡姆剃刀）。
