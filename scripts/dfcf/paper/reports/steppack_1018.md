# CHAIN_STEP_PACK 为什么没省钱 · 10/15 沙盒 base vs new 逐步拆账（10/18 晚）

> 只读分析，零 LLM 调用。数据：`scripts/temp/rerun_20261015-s{base,new}/tok/*.csv`（逐调用 token）+ `~/.claude/projects/C--Users-admin-dev-investment-tool/*.jsonl`（claude -p 会话原文，按真实 user prompt 切段、按 uuid 去掉 fork 复制段，归到 组/0915·盘中/步）。
> 噪声带：同一套会话日志里还能拆出 ab1/ab3/no03 三组（它们的 tok 目录已删，只有会话数），ab1/ab3 当作“base 级别的噪声带”。
> 脚本与中间产物：`scripts/temp/steppack_1018/`（seg.py → classify.py → tools_cmp.py / tok_cmp.py）。
> 价格按 tok 日志反推（R²=1.0）：输入 $4/M，输出 $20/M，**缓存读 $0.2/M**，**缓存写 $5/M**。

## 结论（先说）

1. **素材包确实注入了，模型也基本照做了，但它只装在 0915 全链上**（`step_pack_block` 只在 `_a6_prompt` 里调用，`a6` 只在 0915 非子链时启用）。盘中子链合并会话 sub3 一个字都没加（new 组 sub 的 prompt 里出现 `CHAIN_STEP_PACK` 的比例是 0/80）。
2. **0915 上省是真的**：工具调用 543→414（−24%），Bash 115→21（−82%），grep rules.md 33→0，输入 token 44.6M→37.3M（−16%）；ab1/ab3 噪声带是 511~569 次工具、40.8~45.0M 输入，new 落在噪声带外面。
3. **省钱很少，原因有三个**：
   - 省下来的大多是**缓存读**（7.0M token × $0.2/M ≈ $1.4）；真正花钱的是缓存写（只省了 $4.9）和输出（没变）。
   - new 组 0915 刚好多碰上几次**缓存没命中**（fork 会话的整段上文按原价计费：anlizhuohuo、zhiyingjuexin 两条链整条都没命中），raw 输入多花了 $2.6，把省下的吃掉一半。跟素材包无关（素材包加在新消息里，不在缓存前缀里）。
   - **大头在盘中子链 sub3**：80 个会话，每个平均 16 轮 / 19.6 次工具 / 1.5M 输入，占全天输入的 64%、花费的 53%。代码注释里写的依据“77 个主会话平均 38 轮 / 40 次工具”，77 正好等于 base 组 sub3 会话数——**问题是从 sub3 量出来的，药却开在 0915 上**。
4. **CHAIN_SIZE_RULES 对 token 基本没影响**：只直接造成 1 次回炉（antoo 0927 sub3-06，$0.25），另外 3 次失效线由驱动器自动放宽（0 token）。全天回炉 71→70 次、$16.7→$17.4，在噪声里。
5. **建议：保持开，改两处**。0915 的素材包留着（省得不多，但是真的，也没增加回炉）；**照同样思路给 sub3 做一份**，这才是能省钱的地方（估计每天 $15~30）。具体改法见文末。

## 3. 为什么 token 合计“持平”

## 5. 建议：保持开，改两处

**保持开（0915）**：效果真实（工具 −24%、输入 −16%、每天约 −$5~7），没有带来回炉。

**改 1：给 sub3 合并会话做一份素材包（主要收益在这里）**——在 sub3 prompt 头部（“盘中子链合并调用”那段之后）加：
1. 工作目录清单（复用 `step_pack_block` 的清单那一行）；
2. 内联附上 cand_snap.md、paper_state.json、gate.json（都很小，模型每会话本来就要读/cat 约 1 次）；**01_facts.md 先不附**（24KB，每会话只读 0.72 次，附上去每个会话都要多付一次缓存写，算下来不一定划算——想附就先做 A/B）；facts.txt 不附；
3. 工作方式约定，比 0915 版多两条：
   - “你本会话刚 Write 过的 02/04/05 产物就在上文，**不要再 Read/cat 回来核对**”；
   - “**不要读 scripts/taoge-chain/*.py、matcher.mjs、quality_hooks.py、price_rules.py** 去猜校验规则；校验不过驱动器会把原因发回”；
   - 保留“不自写 python 校验”“rules 按行号 Read”。
4. 预期：每会话少 4~6 轮 → 80 会话 × $0.2~0.4 ≈ **每天 $15~30**（全天 6~12%）。先只在沙盒开（建议另起开关 `CHAIN_SUB_PACK`，跟 0915 的分开，好做消融），跑一天对比 sub3 每会话轮次和花费。

**改 2：0915 版本的小修**
- 从 `STEP_PACK_EXTRA["02"]` 里去掉 `@cs`（02 时这个文件还没生成，每次只换来一句“不存在”）。
- 模板里还写着“按需 grep -n "^### <编号>" rules.md 捞”，和素材包“按行号 Read”打架；模型这次听了素材包的，但建议把模板也统一成按行号 Read，免得以后模型改听模板。
- 04 剩下的工具调用主要是翻历史 K 线：可以给 04 附一张“候选票近 N 日 OHLC 摘要”（驱动器机械生成，类似 cand_snap），再省 1~2 轮。

**比素材包更值钱、建议另开 TODO 的**
- **缓存没命中**：两组每天原价输入 $17~21，几次 sub3 单会话就有 0.8~1.5M 原价输入（一次 $5~7.6）。查 fork/resume 会话被分到别的 key/线路、导致前缀缓存失效的原因（比如同一条链钉同一个 profile），一次修好就跟素材包全部收益差不多。
- 回炉：0915 04 的“direction ∉ 02”每天约 11 次、sub3“总仓”每天 17~19 次，全天回炉约 $17。

## 不自信点

- 只有 1 个交易日、每组 20 条链；0915 的效果超出了 ab1/ab3 噪声带，但幅度（$5~7）跟缓存没命中带来的波动（$2~4）是同一个量级。
- 会话→步骤的归类靠解析 prompt：0915 各步跟 tok 行数对得上（各步 20 次 + 回炉），盘中盲审会话数（base 59 / new 41）比 tok 行数（43/30）多，盘中盲审的数字不精确（不影响结论）。
- ab1/ab3/no03 自己也开了别的开关，拿它们当噪声带是近似；no03 去掉了 03 步，0915 的数不能比，只在盘中用。
- sub3 省钱的估算是线性外推（每轮边际成本 × 少掉的轮数），模型实际会不会少读、少读之后会不会多回炉，要实测。
- 账本硬约束回炉 5→10 是不是 SIZE_RULES 间接引起的，单日样本判断不了。
